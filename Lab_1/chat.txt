# 二、各模块具体应该完成什么

M1 用户与权限管理

完成四类用户角色的权限划分，支持必要的身份识别与登录，并在活动审核、报名、检票、名单访问等操作前进行权限验证。

主要产物：用户与角色模型、权限矩阵、身份认证及权限校验接口。

M2 活动与票务管理

管理活动基本信息、场次、容量、票价以及创建、审核、发布、修改、取消等生命周期。同时处理容量缩减和受影响人员通知。

主要产物：活动管理接口、审核流程、活动状态机、容量变更规则。

M3 活动查询与展示

实现公开活动列表、活动详情、报名资格判断、个人创建或参与的活动查询。后续还需要完善多条件筛选。

主要产物：搜索与筛选接口、活动详情页面、个人活动列表。

M4 报名与候补管理

处理报名申请、剩余名额计算、重复报名、并发抢名额、报名截止、取消报名、候补队列、自动递补以及可能的缺席限制。

主要产物：报名状态机、报名记录接口、候补队列处理机制、并发一致性测试。

M5 电子票与检票管理

为成功报名的用户生成电子票，由检票员扫码完成签到，同时检查票据有效性和报名状态。

主要产物：电子票生成与验证接口、扫码签到流程、签到记录。

M6 数据管理与统计

维护活动、场次、用户、报名和候补记录的关联，补充课程要求的报名名单导出、容量统计及关键操作日志查询功能。

主要产物：数据模型、统计接口、名单导出、日志查询。

其中 M4 是整个系统业务规则最复杂、测试风险最高的模块，需要优先考虑数据一致性；M1 和 M2 则是其他功能能够正常运行的基础。

核心数据实体关系示意

示意图只表达主要实体及可能的关联，不代表最终外键结构。票种、通知和操作日志还需在详细设计时扩展。

我建议至少围绕以下数据对象开展数据库设计：

| 实体              | 主要信息                   |
| --------------- | ---------------------- |
| User 用户         | ID、账户信息、角色             |
| Event 活动        | ID、举办方、名称、状态           |
| Session 场次      | ID、活动ID、时间、地点、容量       |
| Registration 报名 | ID、用户ID、场次ID、报名状态、排序依据 |
| Ticket 电子票      | ID、报名ID、票据状态           |
| CheckIn 签到      | ID、报名ID、检票员、签到时间       |
| Notification 通知 | ID、接收人、通知内容、发送状态       |
| AuditLog 操作日志   | 操作者、操作类型、对象、时间、结果      |

这里有两个值得提前明确的设计原则。

首先，候补人员不一定需要单独建一张表。可以在 Registration 表中用不同状态表示「报名成功」与「候补中」，并保存候补顺序。这样能减少报名与候补之间反复迁移数据造成的不一致。

其次，剩余名额、报名记录和报名状态必须保持一致。例如最后一个名额被两个人同时争抢时，不能只在前端判断“还有一个名额”，而应由后端通过数据库事务等一致性机制保证不会超额报名。

具体的唯一性约束也需要确认：一个用户究竟只能对同一活动报名一次，还是允许对同一活动的不同场次分别报名？这个决定会直接影响数据库设计。

# 四、按照依赖关系安排开发顺序

不建议同时启动全部六个模块。它们存在明确的前后依赖关系。

建议开发路径

1. 第一阶段：基础框架与数据模型

   完成项目初始化、核心数据库结构、用户角色与权限机制，并确定活动和报名状态机。
2. 第二阶段：活动管理与查询

   实现创建活动 → 提交审核 → 管理员审核 → 正式发布 → 用户浏览活动，形成第一条完整业务链路。
3. 第三阶段：报名与候补

   实现正常报名、容量限制、重复提交、名额竞争、取消报名和候补递补。这是核心业务阶段。
4. 第四阶段：检票与扩展管理

   实现电子票、扫码签到、容量缩减、状态变更通知，以及待确认后决定是否实现的缺席限制。
5. 第五阶段：统计、日志与系统测试

   完成名单导出、容量统计、关键操作日志及权限、并发、可靠性等测试。

每个阶段最好都有一个可以验证的结果。例如第三阶段结束时，应该能够演示：

某场次容量为 2 人，A、B 报名成功，C、D 进入候补。A 取消报名后，C 自动递补，D 仍在候补队列中；重复请求不能额外占用名额。

这个例子可以直接转化为后续测试用例。

三、人工审查记录

## REV-001

- 相关需求：REQ-021、REQ-022、REQ-023、REQ-024
- AI 原始内容：AI 在容量缩减、通知、二维码电子票和扫码签到的需求中，将 INT-02 的真实时间和独立来源标记为待核实，并将相关需求标记为待确认。
- 发现的问题：需求初稿生成时，AI 未能确认跟进沟通的来源情况，因此在需求描述中保留了来源待核实的表述。当前已提供 2026-10-19 的 INT-02 记录，需要重新核对该记录是否真实、完整，以及各项需求是否得到甲方明确确认。
- 核对依据：INT-02-L001 至 INT-02-L004。
- 最终处理：修改
- 处理理由：在核实 INT-02 的原始沟通记录后，应删除不再成立的来源疑问，并按甲方实际确认的范围更新需求状态。但对于尚未明确的其他容量调整方案、二维码失效规则及通知失败处理，仍应保留“待确认”，不能因为来源得到核实就将所有实施细节视为已确认。

## REV-002

- 相关需求：REQ-024
- AI 原始内容：系统中现场检票人员扫描专属二维码完成检票和签到。重复扫码、无效票及离线检票规则待确认。
- 发现的问题：AI 虽然识别了重复扫码这一异常情况，但没有明确重复签到请求发生时系统应执行的操作，因此该需求的异常处理尚不完整，无法直接形成明确的测试用例。
- 核对依据：INT-01-L004、INT-01-L005、INT-02-L003、INT-02-L004；实验要求中“支持签到或验票，说明重复签到、缺席和活动取消如何处理”。
- 最终处理：修改
- 处理理由：应补充重复签到、无效二维码和活动取消后的检票规则。

## REV-003

- 相关需求：REQ-025、REQ-026、REQ-027
- AI 原始内容：
  - REQ-025：需由甲方确定活动查询的负载、数据规模和响应时间目标。
  - REQ-026：需由甲方确定报名个人信息的访问范围、保存期限及保护标准。
  - REQ-027：需由甲方确定报名在并发与故障条件下的一致性和恢复指标。
- 发现的问题：三条需求均属于非功能需求，但只描述需要进一步确定的事项，没有明确测试对象、测试条件和量化验收标准，不能直接判断系统是否满足要求。同时，三条需求均处于待确认状态，无法达到实验要求的至少三条已确认非功能需求。
- 核对依据：实验要求最终至少包含三条已确认非功能需求，并要求非功能需求具有明确的对象、条件和判断标准。
- 最终处理：修改
- 处理理由：应分别补充查询性能、个人信息安全及报名可靠性的可测试标准，并向甲方核实。性能需求需要明确数据量、并发用户数和响应时限；安全需求需要明确授权对象及越权测试通过标准；可靠性需求需要明确并发测试条件、容量约束及故障处理要求。
